Chapter 5

Roc's copy rule

Roc has only values, yet it writes a list in place whenever it safely can. Both programs depend on that. The interpreter keeps a JavaScript program's heap in one Roc list, which many of its instructions write; the compiler builds an executable's bytes by appending to one list. Each is fast only while Roc writes its list in place. This chapter states when Roc does, and when it quietly copies the list first. Every later chapter that weighs a cost comes back to it, and “Handing the machine on” gives the three habits the interpreter took from it.

When a write copies §

Roc writes a list in place only while the list has a single owner, and a copy is silent. On RC1 every copy is a use after a consume: a write (List.set, append, Dict.insert) takes the value, and something still reads the old one after it. The copy allocates the whole list again on every such write, so its cost grows with the list.

This book calls that drop the copy cliff. A loop that writes in place pays O(1) a write; the same loop with a second owner pays O(n) a write, and the code reads the same either way.

The technique behind the rule is reference counting with in-place update of a value held once, as in Lean 4 (Ullrich and de Moura, "Counting Immutable Beans", 2019) and Koka's Perceus (Reinking, Xie, de Moura and Leijen, 2021).

Records and boxes §

A record update copies the record around the field it writes, inline sub-records included. A Box carried untouched is free, but every write re-boxes it, one allocation a write. “Handing the machine on” shows both at work on the interpreter's machine record.
