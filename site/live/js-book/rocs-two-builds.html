Compiling JavaScript in Roc Chapters

Chapter 15

Roc's two builds

Roc has two backends. The dev backend (--opt=dev) compiles in about a second and emits code that is mostly stack moves. The release build (--opt=speed) goes through LLVM, compiles slowly, and runs the VM's fib(22) about nine times faster: 99 ms of CPU against about 860 (js/README.md, 2026-11-24). Three findings about the pair have lasted, and each tells a reader which build answers which question.

A dev timing says little §

Dev timings fail to predict release timings, even in direction. On 2026-11-23 a branch of the walker, js-run, the project's first interpreter, which walked the program's tree and has since been deleted, ran fib(22) in 642 ms on the dev build against master's 676, and in 169 ms on the release build against master's 121: faster than master on dev, and 40% slower in release (3b4f9bd1).

Some copies happen only in dev §

The dev build makes some copies the release build skips, at a helper's boundary (“Roc's copy rule” lists three such shapes). The project met one in its own code. When ValueRules was split out, its first version took the engine's whole machine as an open record, and the dev build copied the cells on every write through it: 05-array-push's dev count rose from 3 to 12.73 allocations a pass (d8d6b7fe). The rules now take a small machine of the cells, which the VM lends them (“JavaScript's rules for values”). Such a shape tends to copy in release too once the code around it changes, so the dev counts are held as exactly as the release counts.

Count on dev, time on release §

js/controls/ holds nine small programs, each a loop that does one kind of write. js/controls.shale runs each at 1,000 and 10,000 passes and holds what one more pass allocates, exactly, in both builds: expected.txt for release and expected-dev.txt for dev, where each line explains its allocation. Counts are deterministic, so a change that moves one shows in the dev build's counts within seconds, and most trials end there. Times are taken on the release build, once a change's counts hold, from one shared build (tools/roc_build.shale keys each build by its inputs), as roc-apps' CLAUDE.md (section 9) and js/README.md say.

The interpreter's release build §

A build's time sets the pace of every change, and RC1's release builds were the slowest step in the project's loop. js-vm's release build takes 91 s today (js/README.md's status line). Its first release build took 670 s (29cb46ec), while the VM still imported the walker's module for the value rules. Once those rules moved into a module of their own and the import went (d8d6b7fe), the build fell to 84 s (15686d94). The commits leave the cause of the drop unstated.

The interpreter works RC1's release pipeline harder than most Roc projects do. Jack Scully profiled the compiler on this code at roc-apps' 762c7d3a, where most of a build's time went to SpecConstr, a pass of RC1's release pipeline, and he opened three pull requests against that pass. Each is measured alone, on his machine, against the walker's 271 s release build before them (the pull requests' descriptions):

pull request what it changes js-run's release build
#13408 puts cheap checks ahead of the pass's inlining queries 166 s
#13409 restructures the walk those queries run 63 s
#13410 stops a recursive function from unrolling into its own body; fib.js runs 12% faster and loops.js 14% 83 s

He put the three together at about 12 times faster for this repository's code specifically (Zulip, #off topic > LLVM). They are expected to merge after Roc 0.10, so every build time above is RC1's own.

js-x86 building a program, as of 2026-11-27 §

The compiler turns the question around: how long from a program's source to an executable on the disk? x86/buildrace.shale times js-x86 against roc build of the same race written in Roc, at --opt=dev and at --opt=speed, the build whose executables the races run (x86/buildrace/README.md). The latest verdict, warm builds on a quiet box on 2026-11-27, the medians of three (x86/RACES.md; for the executables, x86/RC2.md, a trial of Roc's next release candidate beside the pinned RC1):

from a race's source to an executable build time the executable it makes
js-x86 30 to 600 ms, big daddy the longest 30 to 45 KB stripped for fib, bank and fourteen (x86/RACES.md); across the races, 0.63 to 1.95 times node's time (“The fib race”)
roc build --opt=dev, warm 0.02 to 0.03 s about 2.3 MB, 10 to 25 times slower than --opt=speed's
roc build --opt=speed, warm 1.05 to 3.50 s 32 to 180 KB, the races' Roc contestants

Only js-x86 builds big daddy. On the three races ported to Roc, js-x86 builds 15 to 50 times faster than --opt=speed (x86/buildrace/PROFILE.md, "The build race, before and after"). Roc's dev build is faster still, and its executables run 10 to 25 times slower than --opt=speed's.
