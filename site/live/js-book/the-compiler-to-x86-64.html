Compiling JavaScript in Roc Chapters

Chapter 3

The compiler to x86-64

js-x86, in x86/, turns a program into a static Linux x86-64 executable, and Roc writes every byte of that file. The instruction encoder (X86.roc), the assembler (Assembly.roc) and the ELF writer (Elf.roc) are Roc modules, and the executable talks to the kernel directly, by the syscall instruction. The product holds no assembler, linker, LLVM or libc, and the executable needs none of them to run (x86/README.md).

The milestones §

x86/README.md plans the compiler as six milestones, and later chapters name them by number:

milestone what it adds state on 2026-11-28
1 hello, world: the instruction encoder, the ELF writer, and the write and exit system calls done
2 numbers and functions: doubles, calls, if and loops done
3 heap values with a bump allocator: objects, arrays, strings, closures, Maps and Sets, the timers, classes done
4 the runtime in the subset: console.log's formatting, Map and Set, and number printing, written in JavaScript and compiled by this compiler next
5 the collector, and the whole corpus held to node the collector done
6 type specialization for long numeric loops begun

The pipeline §

stage what it does
the front end, shared JsToX86.roc imports Parser and Compile from js/roc/ as a package, so the compiler starts from the same Bytecode the interpreter runs (“The front end”)
Lowering.roc turns each function's bytecode into Assembly statements, one instruction's machine code after another; OperatorLowering, BuiltinLowering, CallLowering and IndexLowering each take a family of instructions, and Inlining and five later passes are in “What the compiler leaves to an optimizer”
Assembly.roc lays the statements out as bytes; a jump or a call that names a label gets a placeholder, patched once every label's place is known: backpatching, as in a one-pass assembler
Elf.roc wraps the code as an executable: an ELF header, one program header and one segment, read and execute, mapped at 0x400000
x86/executables.shale Roc's default platform writes text alone to stdout, so js-x86 prints the executable as hex, and this script turns each pair of digits back into its byte

A value in 8 bytes §

A slot of the frame that Compile lays out has to hold any JavaScript value. The compiler fits every value into the 8 bytes of a double by NaN-boxing, the representation LuaJIT and SpiderMonkey use. A double has about 2^53 bit patterns that all mean NaN, and x86-64's arithmetic makes only two of them. So a number is its own double, and every other value is one of the spare NaNs: its top 16 bits are a tag, and its low 48 bits are an address or a constant (x86/roc/Boxing.roc):

top 16 bits value low 48 bits
below 0xFFF9 a number the double's own
0xFFF9 undefined, null, false, true 0, 1, 2, 3
0xFFFA a string its address
0xFFFB an array its address
0xFFFC a plain object its address
0xFFFD a function its closure record's address
0xFFFE a Map, a Set or an iterator its record's address

The two NaNs the processor makes lie below every tag, so a value is a number exactly when its bits are below the first tag shifted into place: one unsigned compare.

A value whose kind the compiler knows skips the test of its tag. The lowering walks each function's instructions keeping the kind of each slot and each place on the bytecode's stack: a number, an Integer, a boolean, a string, an array and so on, or Value, a value whose kind only the run decides. Where two known numbers meet +, the code is one addsd. A Value's tag is tested in line for + and the comparisons, and the runtime does the rest (runtime_add, runtime_compare and their kin). Since a value's bits are the same whatever the compiler knows of it, a place that widens to Value where two ways meet costs zero instructions. A function's parameters and its result take their kinds from the whole program: the lowering runs pass after pass until every call's argument kinds and every return's kind settle (Lowering's items_with_numbers).

The runtime §

Every executable carries the runtime, about 28 KB of machine code and its tables: the start, the allocator, buffered output, console.log's writing of values as node writes them, the array methods, the Maps and Sets, and the timers. It is written in Roc too, as lists of Assembly statements, one instruction a line through the short builders of Emit.roc.

At its start the runtime maps 3 GiB of memory: a heap of 2 GiB, then the collector's mark stack. The heap is cut into pages of 64 KiB, each holding blocks of one size, its size class, and every block starts with a header word that names its kind and size (x86/COLLECTOR.md). To allocate, the runtime takes a block from its class's free list, a chain of dead blocks, or else the next block of the class's current page; past a threshold it collects first. A block whose size the runtime knows when it is built, such as a new object or a small array, is allocated by code in line, where every other block takes a call. And the 256 strings of one byte are made once, in the read-only segment, so taking one character of a string hands out one of those.

Four registers belong to the runtime for the whole run:

register holds
r12 the stack's limit
r13 the runtime's state
r14 the heap's end
r15 the heap's state

executable size

The compiled programs' collector §

Every executable carries a garbage collector in its runtime, a mark and sweep designed in x86/COLLECTOR.md. It works on raw memory, the pages and block headers above, and a reference to a block is its address:

part what it does
the roots every word of the machine stack and the registers that looks like a heap address, found conservatively, as Boehm and Weiser's collector for C finds them (1988)
the mark follows each root into the heap, and traces each block by the kind its header names, setting a bit of the header
the sweep clears each marked block's bit, links each unmarked one onto its size's free list, and frees each page whose blocks all died
the trigger the heap past twice the bytes the last collection kept, and at least 8 MiB

A root may be a number that only looks like an address, so the collector leaves every block where it was allocated, and such a root costs at most some garbage kept alive. The headers and pages came first (a328636), then the mark, the sweep and a torture tier, a run of the tests that collects at every allocation (460b606).

Its test of endurance is big daddy, the broadest race of “The fib race”: a fork of program 54 that lives one day of its small city a round. A floor of 8 MiB on the trigger held big daddy at 8.8 MB, about a twelfth of node's peak on the same run; floors from 2 to 64 MiB kept its CPU time within 8% (x86/COLLECTOR.md, its section on the trigger). At big daddy's full size, 15,000 rounds, the run made 735,302,387 allocations and 7,499 collections, and the heap stayed within 135 pages, 8.8 MB (x86/bigdaddy/README.md, "At full size").

What it compiles, as of 2026-11-27 §

x86/programs.shale compiles each of the 63 corpus programs in js/tests/ and holds those whose executables print exactly what node prints to x86/corpus.txt: 51 of 63 (x86/README.md, "The corpus"). It also holds the 80 programs of x86/tests/ to node and the 50 of x86/tests/refused/ to their refusals (counted on 2026-11-28). The 12 left stop at these, by the first reason each meets:

programs the first reason
3 an error the program leaves uncaught, where node exits 1
4 a number console.log can write only once milestone 4's number printing is written: three fractions, and an integer past 2^53
5 one each: Math.sin, an array of more than 100 items printed, a string beyond ASCII, a call of a number, and an array's at
