Chapter 7

What the compiler leaves to an optimizer

The compiler's code is plain, and “The compiler against node” measures what that costs against V8. A few standard optimizations make it cheaper, and the rest is made the plainest way.

What makes code cheaper §

Each optimization the compiler makes is a standard technique (x86/roc/Lowering.roc's header, x86/README.md):

what the compiler does where the technique
a known kind skips the tag's test, so two known numbers add with one addsd; a whole number proved in range is an Integer, so a loop's counter steps with add and indexes an array as it is Lowering.roc; x86/README.md, "An integer kind" kinds found by iterating to a fixed point, as in dataflow analysis (Kildall, 1973)
a function known by its code is called directly, and keeps the parameter kinds its calls give it Lowering.roc a direct call of a known function
a function known before the program runs takes zero bytes in a slot, and becomes a closure record only where it is used as a value Lowering.roc a closure made only where it escapes
a class's field is read at the place its constructor gives it, and a method from its class's table, each tested in line FieldSlots.roc, MethodTables.roc Self's maps (Chambers, Ungar and Lee, 1989), which V8 calls hidden classes
for what is unknown, the commonest cases are tested in line, and the runtime's routine is called only when the test fails: + and the comparisons of two numbers, a number's tag test, and an array's length, item read and item write OperatorLowering.roc, IndexLowering.roc; 17cb2b0, d6ecebd an inline cache (Deutsch and Schiffman, 1984, for Smalltalk-80)
a small leaf function called inside a loop is put in line in the bytecode, within a budget of instructions Inlining.roc inlining, a textbook optimization
a loop that reads, as numbers, values whose kind only the run decides is placed twice: a guard at its head tests that each such value is a whole number of 32 bits and that each array it reads holds items of one kind; the fast copy after it treats them so, and a failed test runs the general copy Versioning.roc; x86/SPECIALIZATION.md loop versioning
after the lowering, a looping function's four busiest frame places live in registers Registers.roc register allocation by usage counts (Freiburghouse, 1974), the plainest kind, short of graph coloring (Chaitin, 1982)
a load of a frame place that a register already holds becomes a move from that register, and a dead store, one that every later path stores over or leaves unread, is dropped FrameValues.roc; x86/COST.md value numbering (Cocke and Schwartz, 1970) and dead-store elimination by backward liveness
three passes take out loads of what a register already holds, dead register moves, and jumps to jumps Forwarding.roc, Moves.roc, Jumps.roc peephole optimization (McKeeman, 1965) and jump threading

The plain parts §

Everything else is done the plainest way. Each function's frame is fixed: every slot, and every place on the bytecode's stack, has its own address below rbp, and an instruction loads its operands from there into rax or xmm0, works, and stores the result back, or uses the register Registers gave the place; FrameValues then thins that traffic, as its row above says, though it leaves alone any program that holds a try. Each bytecode instruction becomes its own machine code, in order, and a call stays a call but for the inlined leaves. Registers renames at most four places a function, chosen by how often plain moves name them; a search of x86/roc/ on 2026-11-28 finds zero mentions of constant folding.

Where an optimizer would pay §

An optimizer would pay most on loops. The loops program has the widest gap, 6 to 8 times. x86/BENCH.md offers an unmeasured guess: a tight loop over a local array is where V8's registers and small integers help most, and where the executable's trips through memory cost most. A second guess, also unmeasured, is that loops and collatz both use %, which the executable lowers to idiv, one of the processor's slower instructions. The README's milestone 6, type specialization for long numeric loops, is aimed at the first. In the fib race the cost was measured, by reading the machine code: eleven calls into the runtime for each limb, since an array's items are of unknown kind, which the in-line paths cut (x86/race/README.md).

Counting in place of timing §

The races run on the development box, a shared two-core virtual machine in the cloud, where every timing moves with the load, and the cloud's hypervisor hides the processor's own counters from perf (x86/COST.md, "What the box has"). So the executable counts for itself. js-x86's counted mode (x86/roc/Counter.roc, 87d3a96) writes a second executable with one inc of a counter at the start of every block of the code, the runtime's included, and shale x86/cost.shale counted=1 multiplies each block's count by its instructions (b4bb941). The answer is the exact number of instructions the run executed, by place and by function, and it reads the same on a busy box as on a quiet one: run twice, each race's counts matched byte for byte (x86/COST.md, "The counter"). A count is blind to cache misses, so it compares two builds of one race, and the stopwatch still gives the verdict.

Big daddy at 300 rounds shows how a count is read. It ran 6,917,983,458 instructions, 90% of them in the runtime: 31.6% of the run in a Map's or a Set's search for a key, a walk of the entries in order, and 15.3% in comparing strings a byte at a time, most of it for that search (x86/bigdaddy/README.md, "Where we're weak against node"). So the next change was a hashed index (8fc3ab7), which finds a key past 8 entries by its hash, as an object's table already did, and compares strings 8 bytes a step. The run fell to 4,085,933,251 instructions, 40.9% fewer, and the two shares to 3.9% and 2.0%.

The same index took the SAT race's count down by 33.1%, and FrameValues, the change before it, by 21% (x86/bigdaddy/README.md; x86/COST.md). Both came between the SAT race's two timings of “The fib race”, whose ratio to node fell from 2.29 to 1.95 (x86/RACES.md).

What comes next §

Of the milestones listed in “The compiler to x86-64”, milestone 4 comes next: the runtime written in the subset, whose number printing the corpus programs that print fractions wait on. Milestone 6, the type specialization the loops above ask for, is begun: the integer kind, each array's element kind in its header, and the versioned loops (x86/README.md; x86/SPECIALIZATION.md).
