A JavaScript Interpreter in Roc Chapters

Chapter 15

Why a compiler suits Roc

In one respect the compiler is the simpler of the two programs for Roc. An interpreter has to perform the program's effects while it runs. A compiler reads a text and gives back bytes, one transformation from start to end, and the effects wait for the executable.

The interpreter has effects of its own §

The VM runs the program inside the Roc call. When the program calls console.log, the VM hands the line to its host's emit! then and there; a timer waits on the event queue; a click arrives from the page (“A canvas in the browser”). So the VM's loop is effectful, and Roc marks every function on that path with ! and =>: 25 lines of Vm.roc declare such a function, and 38 lines across js/roc/ (lines of the form name! :, counted for this chapter on 2026-11-25).

The run's whole state travels with those calls as one value, the machine, and most of the interpreter's performance work went into handing it on cheaply. The cells are lent to a rule and taken back, so a write to the heap stays in place (“JavaScript's rules for values”). Every shape that would put a second owner on the heap is a copy cliff, and the machine record is held to 248 bytes so that handing it to each instruction costs vector moves in place of a memcpy (“What copies”).

The compiler is one function §

The compiler's whole work is executable_of, from the program's text to the executable's bytes, or the reason it refuses:

Its type, Str -> Try(List(U8), Str), has Roc's thin arrow: a pure function. Each stage it calls is pure too: Parser.program_of, Compile.program, Lowering.program_items, Assembly.assemble and Elf.executable. Across the 13,521 lines of x86/roc/, four definitions carry the ! of an effect: main! and write_program! in each of the two drivers, JsToX86.roc and Hello.roc, which print the bytes (counted for this chapter on 2026-11-25).

The ultimate delegation §

The program's effects still happen, later, and the processor does them. console.log ends in the runtime's runtime_write, which fills the output buffer, and the buffer goes out by a syscall instruction for write. The timers become runtime_run_timers, a loop in the executable over a virtual clock. The compiler writes each effect down as instructions, and the processor and the kernel perform them when the executable runs.

Many compilers hand their last step to a C compiler or to LLVM. This one hands it to the metal: the bytes Roc writes are the bytes the processor runs.

What the copy rule still asks §

With the effects gone, the machine record and its lending go too. The lowering's state is the kinds of one function's slots, made afresh for each function on each pass, and the passes are a plain loop over values that ends when the kinds settle. The one large value that grows is the code itself. Assembly.roc builds the bytes by appending to one list and patches the placeholders with set while that list has one owner, so both passes write it in place (the module's own comment; unchecked by an allocation count). The copy rule of “What copies” still holds, and in the compiler it governs one list in one place.

A pure function is also plain to test. Each of the encoder's 98 expects holds one instruction's bytes, rsp and r12 as a base and the displacements at the edges of 8 and 32 bits among them, and each was read back through objdump during development (x86/README.md). An expect of a pure function needs a value in and a value out, and the host stays out of it.

The work moved, and some of it moved into the runtime. A routine that the interpreter writes as a Roc function, such as console.log's layout of an array in columns, is in the compiler a list of x86-64 instructions, written one a line in Roc (x86/roc/Inspect.roc, 1,184 lines).
