Chapter 10

The interpreter

The interpreter, js-vm, is the other way to run the subset, and the first one built (“How it got here”). Where the compiler turns a program into an executable, the interpreter runs it directly: the front end's bytecode (“The front end”) goes to Vm.roc, a stack machine written in Roc. It runs in two places. From the command line, js/roc/JsVm.roc runs a file, and js/oracle.shale holds every corpus program's output to node's. In the browser, the same VM compiled to wasm is the engine of the playground, where a program draws on a canvas (“A canvas in the browser”).

Because the interpreter keeps a whole run in Roc values, it needs its own memory, its own collector and its own care with copies, the subjects of “Memory strategy”, “The garbage collector” and “Handing the machine on”. This chapter looks at the VM's loop, then at the one value the run works on: the machine.

Beside it, Inspect.roc formats console.log's output as node's util.inspect does, function for function, and NumberText.roc writes a number as String(n) does.

The loop only dispatches §

The VM's loop fetches the next instruction and hands the machine to dispatch!, whose match calls one top-level handler an arm. The heap is one Roc value §

JavaScript shares arrays, objects and closures by reference, and Roc has only values. So the interpreter keeps everything JavaScript shares in one list of cells, the heap, and a JavaScript reference is an index into it. “Memory strategy” lays out the heap, the stack and what each operation costs.
