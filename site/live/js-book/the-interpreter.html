Chapter 9

The interpreter

The interpreter, js-vm, is the other way to run the subset. Where the compiler turns a program into an executable, the interpreter runs it directly: the front end's bytecode (“The front end”) goes to Vm.roc, a stack machine written in Roc. It runs all 63 corpus programs as node does, so it is also the project's reference for what the subset means. It runs in two places:

where what runs held by
the command line js/roc/JsVm.roc, on a file js/oracle.shale, which holds every corpus program's output to node's
the browser the same VM compiled to wasm, the engine of the playground, where a program draws on a canvas (“A canvas in the browser”) js/page_check.mjs (“How it is tested”)

The interpreter keeps a whole run in Roc values, so it needs its own memory, its own collector and its own care with copies, the subjects of “Memory strategy”, “The garbage collector” and “Handing the machine on”. At its centre are the VM's loop and the one value the run works on, the machine.

Beside it, Inspect.roc formats console.log's output as node's util.inspect does, function for function, and NumberText.roc writes a number as String(n) does.

The loop only dispatches §

The VM's loop fetches the next instruction and hands the machine to dispatch!, whose match calls one top-level handler an arm. Each handler is a small function of its own, so the language grows by adding handlers and every function stays small. Here is the heart of the loop. The heap is one Roc value §

JavaScript shares arrays, objects and closures by reference, and Roc has only values. So the interpreter keeps everything JavaScript shares in one list of cells, the heap, and a JavaScript reference is an index into it. “Memory strategy” lays out the heap, the stack and what each operation costs.

Where its time goes §

The interpreter has yet to be profiled instruction by instruction. What is known, as of 2026-11-27:

  • Beside the compiler it is slow, as “The compiler against node” measures.
  • Each instruction is a fetch, a match in dispatch! and a handler's call, and the handler copies the machine record on the way in; “Handing the machine on” gives that copy's cost and the one profile taken.
  • Every instruction also passes the collector's check and the step count, and a property read or write searches the object's own properties, O(p) (“Memory strategy”).

Measuring further is left for later. perf is closed to an unprivileged user on the development box (perf_event_paranoid is 4, x86/buildrace/PROFILE.md), and the samplers that profiled the compiler's code there, one by ptrace and one built into the executables (x86/satrace/TRIAGE.md), have only been pointed at the compiler so far.

The interpreter has effects of its own §

The VM runs the program inside the Roc call. When the program calls console.log, the VM hands the line to its host's emit! then and there; a timer waits on the event queue; a click arrives from the page (“A canvas in the browser”). So the VM's loop is effectful, and Roc marks every function on that path with ! and =>: 25 lines of Vm.roc declare such a function, and 38 lines across js/roc/ (lines of the form name! :, counted for this chapter on 2026-11-25).

The run's whole state travels with those calls as one value, the machine, and most of the interpreter's performance work went into handing it on cheaply. The heap's cells are handed to the code that writes them as their one owner and taken back after, so a write to the heap stays in place (“JavaScript's rules for values”). Every shape that would put a second owner on the heap is a copy cliff, and the machine record is kept small so that handing it to each instruction stays cheap (“Handing the machine on”).
