A riff on Cook-Levin Chapters

Chapter 1

Introduction

Every frame. Start here; it stands alone. Some problems are easy to check and hard to solve: an answer can be confirmed in moments, but finding one can mean a search that doubles with every step. That gap is what makes computation feel intractable, and it is the question at the heart of P versus NP. This book doesn't answer that question. It makes the gap visible on a machine small enough to hold in your head, a toy designed by Steve Howell (six-line programs on four inputs, 4,096 programs in all), and along the way it tries a few ways around it, which sometimes help and sometimes only show how wide the gap is. Then we grow the machine into Nibble++ and find out what surprises.

The thesis. The Cook-Levin theorem turns any fast checker into one Boolean formula, so that a question about the checker becomes a question about the formula. This book does that to a toy machine, all the way through, and checks every step. Its thesis: the machine and its Cook-Levin translation answer every question the same way, whether the machine runs as a program, is wired as gates, is written as clauses for a SAT solver or is composed into polynomials, so the gap you see belongs to the problem itself. The method is a developer's: brute force first, since the toy is small enough to run everything, and refinement after, once the brute force has shown what is there. Steve's 2023 Python first checked that agreement on a handful of programs; this repository checks it on all of them, and finishes the composition he stopped short of (“Six steps composed”).

The machine is called Nibble. Steve Howell invented it in March 2023: one two-bit register, AX, four instructions, nada, zero, decr and mod2, and programs exactly six lines long. Nibble is also the name of its assembly language and of the puzzle page where you can play it. A program accepts some of the inputs 0 to 3 and rejects the rest, so it decides one of 16 problems, and there are only 4,096 programs, so every claim about the machine can be checked by running all of them. Its bigger sibling, Nibble++, has a four-bit AX and programs of any length: 65,536 problems, and far too many programs to list, which is where brute force starts to strain. “The machine” gives the rules in one page.

A fair objection, answered early. A fixed, finite machine answers every question by a table lookup, in constant time, so where does asymptotic theory get a grip? “Nibble, sized” answers it: it gives the machine two sizes, a register of n bits and a program of k lines, and lets them grow, so that P and NP have something to measure.

Program 1689 is your guide. It is zero, decr, decr, zero, decr, zero, the one program that decides {0, 2, 3}. In base 4, 1689 is 122121, one digit a line, with zero as 1 and decr as 2: the number is the program. Each chapter that shows the machine in a new form shows 1689 in it too, in a box headed "1689, here", so a reader who follows the boxes alone sees the whole reduction, from a run to a satisfying assignment. The Nibble++ chapters follow is_not_14's 28-line program the same way, in boxes headed "is_not_14, here".

The monstrosities. This machine fits on an index card: one two-bit register, four instructions, six lines. Yet it keeps producing monsters, and we have numbered them proudly, like theorems. The question "does this program accept this input?", composed through six steps, becomes one polynomial of 510,387 characters (Monstrosity 5). Wiring the same machine as gates takes 1,439 equations (Monstrosity 1). Ask whether the 4-bit Nibble++ can decide is_not_14 in 27 lines, and the answer, that every 27-line program fails, comes backed by a proof of 17,192,870 bytes that our own checker replays line by line (Monstrosity 6), while the answer at 28 lines is a program of 56 bits that you check by running it. That gap is NP's in miniature: a yes has a short certificate, and the best known evidence the other way can be enormous. Skim them, marvel, and move on: each is the hidden complexity in simple things.

Steve wrote the first version by hand in Python, in virtual-machine: the machine (virtual_machine.py), a general polynomial library (poly.py) and a stepper that writes one step of the machine as polynomials (stepper.py). The machine is Steve's invention; the code in this repository, written by AI coding agents (Claude) with human supervision, departs from the 2023 Python wherever a cleaner choice turned up, and its choices are this book's own. Each language has one role, which “The languages in this book” sets out.

Why the name fits §

The Cook-Levin theorem says that satisfiability of Boolean formulas is NP-complete: any problem whose answers a machine can check in polynomial time reduces to it. The proof unrolls the checking machine, step by step, into one formula. This repository does that unrolling on a toy instrument. It makes no claim about NP, and it reduces one machine's questions, never an arbitrary verifier's. It also goes one step past the formula, into arithmetic: the whole program becomes four polynomials with integer coefficients. "A riff" is the honest word for that.

Where the numbers come from §

Each number here comes from the repository, a commit, a golden file or a program run, named where it is used. Code is quoted as it stands when the book is built. Under each theorem a "Run it" box gives the command that checks it, from the repository's root once shale build.shale has built the tests, and the line it prints; the book's build holds each line to its test file.

So every claim in this book comes with a run that checks it, on a machine small enough to hold in your head.
