Moving to Roc 0.1.0 RC1

Roc's first release candidate, 0.1.0_RC1, is out, and we have moved seven of our eight Roc projects to it. The eighth, roc-chat, is still moving, and each place on this page that waits for it says pending. This page is for Richard Feldman and the Roc team: what the move cost us, what it turned up, and how long our builds take on each compiler. Each thing worth reporting has a reduced program beside it.

Claude, an AI coding agent, made the moves, ran the measurements and wrote this page under Steve's supervision. Every commit linked here is on GitHub.

Summary

  • RC1's dev builds default to "boxy" specialization. Our chess proof, KnightProof, ran 22 times slower at run time built with --opt=dev: 344.7 s of CPU, against 15.6 s on the old nightly. --specialize=yes brings it back to 15.8 s, and the chess gate, the one dev-built check whose run time it moved, now passes it. Read more below.
  • A "duplicate definition" warning we think is a false one. A nested type's member that shares a name with a member of the type around it (Crate.width and Crate.Lid.width) gets the warning. The program runs correctly, and we have a reduced repro. roc-chat has five such sites, and renaming them so it can move now is pending. Read more below.
  • The stricter nominal-type check caught a real mistake in our code. Our Safari code passed a plain record where the nominal type Cat (and Bird) was wanted, and the old nightly accepted it. The check also finds 15 errors in roc-ray's platform, Luke Boswell's repository, which we don't maintain. Read more below.
  • A new shadowing warning. A parameter named like a definition at its module's top level, a type's own members included, now gets a "duplicate definition" warning. It found 88 real shadows in our code. Read more below.
  • Unsuffixed number literals no longer get a concrete type from a method call on them. (0.0).to_bits() is now a "missing method" error; (0.0.F64).to_bits() is fine. Read more below.
  • Glue changes. The erased callable's payload gains on_copy and capture_size, and there are new RocOpaqueList and RocHeldList types. Our seam checks caught both, and the regenerated glue was all our hosts needed. Read more below.
  • RC1 calls each hosted function through a generated wrapper, which moved where Shale's Roc platform says a script stopped. A frame-pointer walk in the host fixed it. Read more below.
  • Build times. Cold checks took more CPU in two of our four measured repositories and less in one. Warm checks, dev builds and tests were mostly 10 to 40 times faster, and rebuilds after an edit were faster by less. Release builds took the same time or less, and their outputs are about 10% bigger. Read more below.

What moving cost us

One line for each kind of change, with its reason:

  • 88 parameters and locals renamed (48 in roc-chat, 31 in roc-apps, 5 in Shale, 4 in roc-screensaver), for the shadowing warning. Our gates fail on any warning.
  • 14 number literals given a type (5 in roc-apps, 9 in roc-screensaver), for literal typing.
  • Safari's Cat and Bird built as nominal values where an encounter places them, for the nominal check.
  • Shale's stop sites found by a frame-pointer walk, for the hosted-call wrapper.
  • The glue regenerated in roc-screensaver, Shale's Roc platform and roc-apps' book_builder, for the glue changes. roc-types also passes BuildEnv.init its new seventh argument, the specialization strategy.
  • One flag, --specialize=yes, in the chess gate, for the boxy default.
  • The native roc-ray builds retired. In Steve's words: "we have had successful roc-ray builds in the past but stopped verifying native builds after some compiler churn". roc-ray's platform doesn't compile at RC1, and it isn't ours to move, so the canvas apps now run as web pages only.
  • roc-types' release build stripped of debug info, to get past an LLVM assertion in Zig 0.17.1 (our patched build). That one is Zig's, not Roc's.

Much of that wasn't really a cost. Some of it was code that was wrong to begin with: parameters that hid their own function, and a plain record passed where a nominal type was wanted. Our own Safari book taught metres = |metres| as an example. In those places RC1 surfaced our mistakes.

Dev builds default to boxy specialization

At RC1, roc build --opt=dev lowers a program the boxy way unless --specialize=yes asks for lambda-set specialization. Safari's proof tools, also built with --opt=dev, took 56 s with the flag and without it. KnightProof, the Knight's Tour proof that the chess gate builds with --opt=dev, ran 22 times slower: the table above has the numbers. With the flag, it runs as fast as it did on the old nightly. The chess gate now passes it, with the reason beside it:

If boxy is the intended default for dev builds, that's fine for us: we pass the flag where run time matters. We report it because a 22 times slowdown in a dev build is easy to mistake for a bug in one's own program.

Hosted calls through a wrapper

Shale runs Roc scripts on a platform of its own, and when a script stops, the host names the script's line by looking up the hosted call's return address in the program's line table. RC1 calls each hosted function through a generated wrapper, and the line table puts that wrapper on a line of the app's root module. So a stop was put on that line of the root instead of the call's own, and six recipes' self-tests and goldens failed in Shale's full tier.

Build times

We timed four repositories' Roc builds on the old nightly and on RC1, under the four conditions Richard's RC1 announcement names:

  • cold: Roc's cache emptied, then a hello-world app built, so only the builtins are cached;
  • warm: the same step again at once;
  • root changed: a comment line appended to the step's root module;
  • import changed: a comment line appended to the module the repository's own modules import most.

Each number is the median of three runs, in seconds, of roc check, roc build with --opt=dev and with --opt=speed (where the repository ships a release build), and roc test. The two compilers took turns within each repetition, so both saw the same box. Each run was niced to 19 and had a throwaway cache of its own. The script is tools/measure_roc_builds.shale, and the TSV has every run, its CPU time and the box's load.

The numbers are noisy, because the box was doing other work (below). Some spreads are wide: roc-syntax-color's three cold checks took 0.58, 7.44 and 9.47 s on the old nightly and 10.64, 21.30 and 22.32 s at RC1, while their CPU time was about 0.5 s and 1.3 s. Most of that wall time isn't the compiler's CPU, and we haven't found where it goes. One cold release build of roc-screensaver took 115.5 s where the other two took about 17 s. Read the CPU columns beside the wall ones, and treat a difference under about 2 times as noise unless the CPU time agrees.

What the numbers say, with that in mind:

  • Cold checks took about 2.4 times the CPU at RC1 in roc-syntax-color and roc-markdown, about the same in roc-screensaver, and less in roc-apps.
  • Warm checks, dev builds and tests were 10 to 64 times faster at RC1, with two outliers: roc-markdown's warm check (3 times, both under 0.1 s) and roc-screensaver's warm test (over 100 times).
  • After a change to the root module, they were mostly 4 to 32 times faster, and roc-screensaver's test 75 times. Two checks gained less: roc-markdown's (0.07 s against 0.04 s) and roc-syntax-color's, which wasn't faster (0.12 s against 0.20 s). Both are small enough to be noise. After a change to an imported module, they were 1.3 to 8 times faster.
  • Cold dev builds took about the same time on both, and less at RC1 in roc-apps. Cold tests were mixed.
  • Release builds took the same time in roc-markdown and less at RC1 in roc-screensaver and roc-apps.
  • Release outputs are 8 to 13% bigger at RC1. Dev outputs are bigger in three repositories and half the size in roc-apps, whose dev build is wasm.

The box

Every number here comes from one DigitalOcean droplet: 2 CPUs (Intel, under KVM), 7.8 GiB of memory and no swap, running Ubuntu 24.04. Several agent lanes share it, and it is not always a clean box: we don't need a clean box to run the builds, and waiting for one would hold up the work. So each row of the TSV records the one-minute load average when its step began, and for roc-screensaver and roc-apps how many other Roc, Zig, Node and Shale programs were running then.

What we found

This is a positive report. Moving seven projects to a release candidate was mostly renames, and here is what we got for it:

  • The stricter checks caught real mistakes in our code. The nominal check found a plain record standing in for Cat and Bird that the old nightly let through.
  • The shadowing warning found 88 real shadows, parameters that hid the definitions beside them, one of them in our own book's teaching example.
  • Testing a release candidate turned up a couple of things to report: the boxy default's cost to one program, and the warning for a nested type's member. That's what a release candidate is for.

One detail of the toolchain, in case it helps anyone else pin RC1: the 0.1.0_RC1 tag points at 15177e9, three commits before 2eadd079, the commit the announcement names. Our pins name 15177e9, which the release's binaries were built from.
