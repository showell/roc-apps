Moving to Roc 0.1.0 RC1

We ran RC1 across seven real projects, about 132,000 lines of Roc, and all their Roc checks are green on it. The eighth, roc-chat (45,000 lines), is still moving.

Roc's first release candidate, 0.1.0_RC1, is out, and each place on this page that waits for roc-chat says pending. This page is for Richard Feldman and the Roc team: what the move cost us, what it turned up, and how long our builds take on each compiler. Each thing worth reporting has a reduced program beside it.

Claude, an AI coding agent, made the moves, ran the measurements and wrote this page under Steve's supervision. Every commit linked here is on GitHub.

What we ran

Each project below ran these checks at RC1, and all of them passed (roc-chat's are pending):

  • roc-apps: roc check of its 51 apps with no errors or warnings and 414 files formatted; Safari's gate (974 expects, 20 widgets built and 1089 of their tests, the tutorial, the proof, the page's drawing held to its frozen checksum); the chess gate; Dog Park's checks; Seattle Delivery's tests; book_builder's verify.
  • roc-screensaver: its 34 checks, among them roc check of 9 roots with no errors or warnings, roc test at its held counts, the PNG harness's frame checksums unchanged, the Windows cross-builds, and the three pages built with --opt=speed and seen running in a headless browser.
  • Shale: its Roc platform's self-test (15 runs held) and roc check of the cookbook's and the platform's 31 Roc roots, no errors or warnings.
  • roc-markdown and roc-syntax-color: their gates, green.
  • roc-types and roc-ast, our two tools built on the compiler's own code: rebuilt against RC1's commit, tested and published.

Summary

Possible issues for the Roc team

  • RC1's dev builds default to boxy lowering, without lambda-set specialization (every roc build but --opt=speed does). Our chess proof, KnightProof, ran 22 times slower at run time built with --opt=dev: 344.7 s of CPU, against 15.6 s on the old nightly. --specialize=yes brings it back to 15.8 s, and the chess gate, the one dev-built check whose run time it moved, now passes it. Read more below.
  • A "duplicate definition" warning we're unsure is intended. A nested type's member that shares a name with a member of the type around it (Crate.width and Crate.Lid.width) gets the warning. The program runs correctly, and there is a reduced repro. roc-chat has five such sites, and renaming them so it can move now is pending. Read more below.
  • Cold checks took about 2.4 times the CPU in two of our four timed projects, roc-syntax-color and roc-markdown (still under 1.5 s of CPU each); about the same in roc-screensaver, and less in roc-apps. Read more below.
  • Release outputs are 8 to 13% bigger. A small thing, noted for completeness. Read more below.

Things we simply had to fix in our own code

  • The new shadowing warning: a parameter named like a definition at its module's top level, a type's own members included. We renamed 88 real shadows. Read more below.
  • Unsuffixed number literals: RC1 no longer settles a literal whose only constraints are method calls ((0.0).to_bits()); we gave 14 of them a type. Read more below.
  • The stricter nominal-type check caught our Safari code passing a plain record where Cat and Bird were wanted, a real mistake the old nightly let through. Read more below.
  • Glue changes: the erased callable's payload gains on_copy and capture_size, and there are new RocOpaqueList and RocHeldList types. We regenerated our glue, and our seam checks passed against it. Read more below.
  • Where Shale reports a script's error. RC1 calls each hosted function through a generated wrapper, which moved the line Shale's Roc platform named when a script stopped; a frame-pointer walk in its host fixed that. Read more below.
  • The native roc-ray builds retired. roc-ray, Luke Boswell's platform, hasn't moved to RC1 yet (the nominal check finds 15 errors in our checkout of it), so our canvas apps run as web pages only. Read more below.

What moving cost us

One line for each kind of change, with its reason:

  • 88 parameters and locals renamed (31 in roc-apps, 48 in roc-chat, 5 in Shale, 4 in roc-screensaver), for the shadowing warning. Our gates fail on any warning.
  • 14 number literals given a type (5 in roc-apps, 9 in roc-screensaver), for literal typing.
  • Safari's Cat and Bird built as nominal values where an encounter places them, for the nominal check.
  • Shale's error lines found by a frame-pointer walk, for the hosted-call wrapper.
  • The glue regenerated in roc-apps' book_builder, Shale's Roc platform and roc-screensaver, for the glue changes. roc-types also passes BuildEnv.init its new seventh argument, the specialization strategy.
  • One flag, --specialize=yes, in the chess gate, for the boxy default.
  • The native roc-ray builds retired. In Steve's words: "we have had successful roc-ray builds in the past but stopped verifying native builds after some compiler churn". roc-ray hasn't moved to RC1 yet, and it isn't ours to move, so the canvas apps now run as web pages only.
  • roc-types' release build stripped of debug info, to get past an LLVM assertion in Zig 0.17.1 (our patched build, 0.17.1+patched.3). That one is in our patched Zig's LLVM, not in Roc.

Much of that wasn't really a cost. Some of it was code that was wrong to begin with: parameters that hid their own function, and a plain record passed where a nominal type was wanted. Our own Safari book taught metres = |metres| as an example. In those places RC1 surfaced our mistakes.

Dev builds default to boxy lowering

At RC1, every build but --opt=speed lowers a program the boxy way unless --specialize=yes asks for lambda-set specialization. roc build --help says so: "Use lambda-set specialization (yes, the --opt=speed default) or boxy lowering (no, the default otherwise)". Safari's proof tools, also built with --opt=dev, took 56 s either way. KnightProof, the Knight's Tour proof that the chess gate builds with --opt=dev, ran 22 times slower. If boxy is the intended default for dev builds, that's fine for us: we pass the flag where run time matters. We report it because a 22 times slowdown in a dev build is easy to mistake for a bug in one's own program.

Hosted calls through a wrapper

Shale runs Roc scripts on a platform of its own, and when a script stops, the host names the script's line by looking up the hosted call's return address in the program's line table. RC1 calls each hosted function through a generated wrapper, and the line table puts that wrapper on a line of the app's root module. So a stop was put on that line of the root instead of the call's own, and six recipes' self-tests and goldens failed in Shale's full tier.

Our fix doesn't depend on the answer, but the wrapper's line-table entry pointing at a line of the root module may be worth a look: if a wrapper should carry no line, or its call site's, a platform that reads return addresses would never meet this.

Build times

We timed four repositories' Roc builds on the old nightly and on RC1, under the four conditions Richard's RC1 announcement names:

  • cold: Roc's cache emptied, then a hello-world app built, so only the builtins are cached;
  • warm: the same step again at once;
  • root changed: a comment line appended to the step's root module;
  • import changed: a comment line appended to the module the repository's own modules import most.

Each number is the median of three runs, in seconds, of roc check, roc build with --opt=dev and with --opt=speed (where the repository ships a release build), and roc test. The two compilers took turns within each repetition, so both saw the same box. Each run was niced to 19 and had a throwaway cache of its own. The script is tools/measure_roc_builds.shale, and the TSV has every run, its CPU time and the box's load.

The numbers are noisy, because the box was doing other work (below). Some spreads are wide: roc-syntax-color's three cold checks took 0.58, 7.44 and 9.47 s on the old nightly and 10.64, 21.30 and 22.32 s at RC1, while their CPU time was about 0.5 s and 1.3 s. Most of that wall time isn't the compiler's CPU, and we haven't found where it goes. One cold release build of roc-screensaver at RC1 took 115.5 s where the other two took about 17 s, and the old nightly's release builds there had outliers of 63 to 86 s too. Read the CPU columns beside the wall ones, and treat a difference under about 2 times as noise unless the CPU time agrees.

What the numbers say, with that in mind:

  • Cold checks took about 2.4 times the CPU at RC1 in roc-syntax-color and roc-markdown, about the same in roc-screensaver, and less in roc-apps.
  • Warm checks, dev builds and tests were 10 to 64 times faster at RC1, with two outliers: roc-markdown's warm check (3 times, both under 0.1 s) and roc-screensaver's warm test (over 100 times).
  • After a change to the root module, they were mostly 4 to 32 times faster, and roc-screensaver's test 75 times. Two checks gained less: roc-markdown's (0.07 s against 0.04 s) and roc-syntax-color's, which was slower by wall time (0.12 s against 0.20 s) and faster by CPU (0.05 s against 0.02 s). Both are small enough to be noise. After a change to an imported module, they were 1.3 to 11 times faster.
  • Cold dev builds took about the same time on both, and less at RC1 in roc-apps. Cold tests were mixed.
  • Release builds took the same time in roc-markdown and less at RC1 in roc-screensaver and roc-apps.
  • Release outputs are 8 to 13% bigger at RC1. Dev outputs are bigger in three repositories (roc-syntax-color's 2.3 times, 1.24 MB to 2.88 MB; we don't know whether boxy lowering explains it) and half the size in roc-apps, the one wasm dev build we measured.

The box

Every number here comes from one DigitalOcean droplet: 2 CPUs (Intel, under KVM), 7.8 GiB of memory and no swap, running Ubuntu 24.04. Several agent lanes share it, and it is not always a clean box: we don't need a clean box to run the builds, and waiting for one would hold up the work. So each row of the TSV records the one-minute load average when its step began, and for roc-screensaver and roc-apps how many other Roc, Zig, Node and Shale programs were running then.

What we found

This is a positive report. Moving seven projects to a release candidate was mostly renames, and here is what we got for it:

  • The stricter checks caught real mistakes in our code. The nominal check found a plain record standing in for Cat and Bird that the old nightly let through.
  • The shadowing warning found 88 real shadows, parameters that hid the definitions beside them, one of them in our own book's teaching example.
  • Testing a release candidate turned up a couple of things to report: the boxy default's cost to one program, and the warning for a nested type's member. That's what a release candidate is for.

One detail of the toolchain, in case it helps anyone else pin RC1: the 0.1.0_RC1 tag points at 15177e9, three commits before 2eadd079, the commit the announcement names. Our pins name 15177e9, which the release's binaries were built from.
