Security idioms in roc-chat

roc-chat is a chat server written in Roc, live at chat.lynrummy.com. In November 2026, notramo tested the live site as a black box and reported what he found. We fixed each bug. For the bigger ones, we then looked for the class each belonged to, and added a type or a check aimed at the whole class. Each section says what its type or check can't see. Two of the bugs here came from our own follow-up, a Markdown spec and an audit of what each request costs; the page says which.

Claude, an AI coding agent, wrote the fixes, the checks and this page under Steve's supervision. Every snippet is quoted from roc-chat at commit 53fe270, its main branch when this page was written, with a link to its lines.

What the types already said

roc-chat's types already answered one question well: who is acting? A route that only the acting user may take asks for a SignedIn in its type, and a SignedIn comes from a checked session or a checked agent key. (One escape hatch checks nothing; only the first start, the demo page and tests call it.) None of the bugs below got past that.

Each bug was a question the types didn't ask. Whose credential is this call changing? What else must happen after this write? What does this request cost? Each fix adds one of those questions, as a type where a type can ask it, and as a check where it can't.

What we'd ask of Roc

These are recommendations from one project's experience. The first is the one this page keeps running into.

Linear types

A value of a linear type must be used exactly once: it can't be copied, and it can't be dropped. An affine type is looser: at most once, so it can't be copied but may be dropped. Roc has neither. It tracks at run time whether a value is unique, to update it in place, but the type checker doesn't. Roc already goes part of the way: a statement must evaluate to {}, so a function's result can't be dropped by accident. (At our pinned nightly, an opaque type whose backing type is {} slips past that rule; a token carrying a user's id doesn't.) But _ = revoke!(...) drops it on purpose and compiles.

Three places on this page would use linear types:

  • A revocation that must be ended. Each revoking write would return a linear value naming whose streams to end, and only UserStreams.end_every_stream! would take it. A sign-out that forgot the ending, on any path, early returns included, would fail to compile. That would replace the check's unended_streams finding, and close two of its gaps: the check judges by line order, not by path, and it reads names, not values, where the value would carry the user. It would also keep the layers apart: the writer returns the value and the action ends the streams. It still wouldn't decide which writes revoke something; the table's ends and keeps stay a reader's call. And it can't help with a crash between the write and the ending, or a file edited by hand.
  • A proof spent once. If replace_password_hash! consumed its AccountProof, a proof could set one password, once, and couldn't be kept for later. An affine type is enough for this. Today the proof is opaque but can be copied, so code holding one could call the writer twice. No code does, and the credential table names the one caller, but the type would make it impossible. It wouldn't replace the credential check, which also covers the writers that take no proof.
  • A claim spent by its join. A linear HumanClaim.Unclaimed would be spent by the join that redeems it, so one judgment couldn't serve two joins. Today the invite's own state, spent after one join, stops a second redemption at run time. Linearity alone wouldn't tie the claim to the invite's human, though. That is the runtime id check in HumanInvites.join. To retire it, one loader would also have to hand back the claim and the invite as a single value.

Nothing else, so far

The other gaps on this page are our own design choices, not Roc's. For example, the platform's answer is a plain record, so any module could set its stream fields. Roc's opaque types would let us close them, and that is ours to do.

What Roc already gives us

Current Roc already does a lot for a service like this. A pure function can't do I/O, and every effect is marked by ! and =>, so a reader can see where the effects are. An opaque type is the only way to make its values, which is what AccountProof and HumanClaim stand on. match is exhaustive, which is what RouteCost depends on, and there are no nulls.

Streams that outlived a sign-out

The bug

The devices page has a button, "Sign out other devices" (POST /devices/sign-out-others). It revoked every other device's key and advanced the session generation, so no old session cookie worked again. But a page's live updates come over an event stream, and the server judges a stream once, when it opens, then holds it for up to an hour. So a stream opened with a stolen cookie kept hearing Recent's tiles, notices and a conversation after the owner signed the other devices out. A join by an invite and a GitHub link end every session too, and they left streams open the same way. (Since the invite fix below, a join is only ever a first join, with no session to end; it still ends streams, to be safe.)

The fix: one place ends a user's streams

UserStreams.end_every_stream! is the one place the app ends a user's streams. The host does the ending; this function names whose.

app/UserStreams.roc, lines 1-23

## This module ends a user's open streams, the one place the app does. A
## stream is judged once, when it opens, and the host holds it for up to an
## hour (`Limits.stream_most_ms`) without asking again, so every action in
## the app that ends a session, revokes a credential or removes someone's
## access calls `end_every_stream!` after its write: each stream reconnects
## and is judged again, admitted only by what still admits it.
## tools/check_stream_endings.shale holds the app to that, and to every
## holder `StreamHolder` names being one this module ends.
import pf.Host
import StreamHolder
import UserId

UserStreams :: [].{

	## Every stream the user `id` holds ended now, under each holder
	## `StreamHolder` names: their pages' streams (a conversation's, Recent's
	## and the device code page's) and an agent's own stream.
	end_every_stream! : UserId => {}
	end_every_stream! = |id| {
		Host.end_every_stream_of_holder!(StreamHolder.user(id).to_bytes())
		Host.end_every_stream_of_holder!(StreamHolder.agent(id).to_bytes())
	}
}

It ends streams under each holder StreamHolder names. StreamHolder is an opaque type, the one home of those names, and HttpAnswer.stream takes one. HttpAnswer.stream is the only code that makes a stream answer today. The platform's answer is a plain record, though, so that is a habit the code keeps, not something the types enforce.

Why a check, and not a type

The rule is "after this write, also do that." In Roc today, a type can demand a value before a call. It can't demand a step after one. We considered a Revocation value that each revoking write would return, and that only ending the streams would take. Roc refuses a statement whose value isn't {}, so a caller couldn't drop it by accident. But with no linear types, _ = drops it on purpose, and that compiles. The other way to force it, ending the streams inside the writer itself, would put the ending in the wrong layer. In roc-chat only FileFacts touches files, through each feature's *Files module, and those modules do only file work; they decide nothing.

So a check holds the rule. tools/check_stream_endings.shale reads every app module with Roc's own parser. Every function that writes a file is judged once in tools/stream_endings.txt: ends if its write ends a session, a credential or someone's access, and keeps if not. Separately, an exempt line names a function and an ends writer it calls that needs no ending there, with the reason.

tools/stream_endings.txt, lines 18-49, trimmed

ends    AccountFiles.replace_password_hash!        a new password ends every session signed over the old one
...
ends    AccountFiles.replace_session_generation!   "Sign out other devices": every session signed before admits no one
ends    AgentFiles.replace_agent_key_state!        an agent's key revoked
ends    DeviceKeyFiles.revoke_device_key!          a device's key revoked, and the session bound to it
...
keeps   AgentFiles.create_agent_key!               a new key admits; it ends nothing
...
exempt  ChannelMembersRoute.add!  DirectoryFiles.replace_channel_members!  adding a member removes no one's access

Then the check walks the calls. Any function outside a *Files module that calls an ends writer, directly or through a *Files function, must call UserStreams.end_every_stream! after it, unless an exempt line names that call. These are its findings:

tools/check_stream_endings.shale, lines 17-31

--   unjudged_writer   a function that writes a file and has no `ends` or
--                     `keeps` line, so a new writer is judged when it comes;
--   stale_entry       a line for no function, an `ends` or `keeps` line for
--                     a function that writes no file, or an `exempt` line
--                     for a call the function doesn't make or that reaches
--                     no `ends` writer;
--   unended_streams   a function outside a `*Files` module that reaches an
--                     `ends` writer (directly, or through a `*Files`
--                     function that calls one) and calls no
--                     `UserStreams.end_every_stream!` after that call;
--   stray_ending      `Host.end_every_stream_of_holder!` called anywhere but
--                     `UserStreams.end_every_stream!`;
--   unended_holder    a `StreamHolder` function that makes a holder (every
--                     one but `to_bytes`) that `UserStreams.end_every_stream!`
--                     doesn't call, so a stream held under it would outlive

The gate, tools/verify.shale, holds it at zero. A new writer fails it until someone judges it, so the table can't go stale. Planted faults show it sees: removing the ending from sign_out_others!, the original bug, gives unended_streams.

What it doesn't catch: it reads names, not values, so it can't tell whether the ending names the same user as the write. It checks that an ending comes later in the function than the first revoking call, by line, not that every path reaches it: an early return between the two would pass. It can't see a writer reached as a method on a value; every writer is called by its module's name today. And it covers the app's own actions: a password or GitHub file edited by hand on the server, or a crash between the write and the ending, leaves a stream open until its hour. The end-to-end tests cover the real cases: an open stream ends on "Sign out other devices", on a GitHub link, on a sign-out, on an agent key's revoke and on a member's removal.

An invite that acted as a password reset

The bug

An inviter could make a new link for a human who had already joined. Redeeming that link set whatever password the redeemer chose, and ended the joined human's own password and session. So whoever made the link could take over the account. It was broken object-level authorization: the password's writer took a bare user id, and nothing in its type said whose proof stood behind the call.

The fix: a claim, and a proof the writer demands

HumanClaim judges a human Unclaimed (no password, no GitHub link, no invite spent) or Claimed. Unclaimed is opaque, and only judge makes one.

app/HumanClaim.roc, lines 11-39

HumanClaim :: [].{

	## What decides it, as the human's files hold them: each invite's state
	## (`HumanInvite.State`).
	Facts : {
		password : [NoPassword, HasPassword],
		github : [NotLinked, Linked],
		invites : List([Live, Spent]),
	}

	## A human with no password, no GitHub link and no invite spent: the only
	## human an invite is made for, or redeems for. Only `judge` makes one.
	Unclaimed :: Users.Human.{

		## The human who has claimed nothing.
		human : HumanClaim.Unclaimed -> Users.Human
		human = |HumanClaim.Unclaimed.(unclaimed)| unclaimed
	}

	## Whether `human`, whose files say `facts`, is `Unclaimed`, or has
	## `Claimed` their account.
	judge : Users.Human, HumanClaim.Facts -> [Unclaimed(HumanClaim.Unclaimed), Claimed]
	judge = |human, { password, github, invites }|
		if password == NoPassword and github == NotLinked and !invites.contains(Spent) {
			Unclaimed(HumanClaim.Unclaimed.(human))
		} else {
			Claimed
		}
}

Writing an invite takes an Unclaimed, so the chat writes no invite for a human who has joined. Inviting one again is a 403 saying a new link would change nothing. A join judges the link's invitee first (InviteRights.load_unclaimed_invitee!), and redeeming takes the Unclaimed that gives, so a link made before the human joined redeems nothing after.

To see that the types hold, we planted calls to create_human_invite! and replace_password_hash! with a bare id. roc check refused both. What the types prove is that judge ran and that a first join made the proof. Which facts reach judge is the loader's job, read from the human's files, and which human a join redeems for is a runtime check: HumanInvites.join compares the Unclaimed human's id with the invite's. Once a human has joined, nothing in the app changes their password: the only AccountProof is a first join's, and there is no admin reset.

The check: every path to a credential, judged

AccountProof guards one writer. The chat has more credentials than a password: GitHub links, session secrets and the session generation, device keys, device codes, agent keys and invites. tools/check_credential_writers.shale holds them all to one table, tools/credential_writers.txt. Every function that writes a file is a writes line, marked credential or other. Every call of a credential writer is a calls line naming the caller and the proof that guards it:

tools/credential_writers.txt, lines 30-59, trimmed

calls AccountFiles.replace_password_hash! HumanInvitesRoute.join_by_invite! unclaimed an AccountProof of a first join: the account's live invite code, redeemed only for a human who has claimed nothing (InviteRights.load_unclaimed_invitee!)
...
calls DeviceSessionsRoute.sign_out_others! DeviceSessionsRoute.sign_out_other_devices! own-session acting.human_in_session(): the acting human's own devices, by a full session (FullSessionRoutes)
...
calls InviteFiles.create_human_invite! HumanInvitesRoute.issue_invite! unclaimed a HumanClaim.Unclaimed, which InviteRights.load_unclaimed! makes only for a human with no password, GitHub link or spent invite, so an invite again for a joined human is refused (Joined)

A proof is one of a short list that are the account's own: own-session, own-github, own-code, unclaimed, agent-keeper, or revokes (it only ends or spends a credential). A caller that only passes the write on is marked passes-on, and its own callers are judged in turn. The gate holds three counts at zero: a writer or a call the table doesn't name, a line for code that is gone, and a proof that isn't the account's own. Before the fix the invite was that last one.

What it doesn't do: it reads lines with regular expressions, not the parse tree, so it sees a call written by its name, and not a writer passed as a value or called as a method. And it can't decide whether a proof is really the account's own; a reader decides that, once, on each line. What the check promises is that no path to a credential goes unjudged.

Smaller fixes

These three bugs weren't type questions. The first two came from notramo's testing, the third from our own Markdown spec.

A reload after a refused sign-in

A refused device code was answered at /login/code, whose GET was a bare 405. Enter in the address bar showed "POST only", and a reload of any refused sign-in posted again. Now a GET of /login/code is a 303 to /login, and the sign-in script puts its form's own GET page in the POST's place in the history (history.replaceState). The sign-in routes are one match over each path and method (sign_in_choice), and these are its lines for /login/code:

app/Route.roc, lines 431-433

(LoginCode, Get) => Open(ReturnToLogin)
(LoginCode, Post) => Open(RedeemDeviceCode)
(LoginCode, Other) => MethodNotAllowed(GetAndPost)

A doubled header

The Caddy site block in front of the chat added X-Content-Type-Options: nosniff on top of the app's own, and Mozilla's Observatory scored the doubled header invalid. The app sends it on every answer it makes (the host's own refusals, such as a 413 or a 429, are plain text and carry none), and the end-to-end tests check it on pages, scripts, images and streams, so the site block no longer adds one.

A class from a message

roc-chat's own Markdown spec found this one while testing what a message can put in the page. A form feed or a CR in a code fence's info string stayed in the language's name: ```x<FF>top-bar rendered class="language-x<FF>top-bar", which a browser reads as two classes. So a message could give its code block any class of the page's own. In roc-markdown, a fence's language now ends at any of HTML's spaces.

What a request costs

The bug

A client with no account can still make the server work. Our audit of what each request costs found that every request read the whole directory of accounts and channels from disk, twice: once to judge the request's head and once to answer it. At 300 humans a request for the favicon made 1,804 file reads. Nothing in the code said which routes may grow with the chat, so nothing caught it.

The fix: every route declares its cost

RouteCost.growth_of gives every route a cost class: Constant (the same file calls however many humans the chat has), PerReaderPlaces (a listing for each place the reader may open) or PerHuman (a read of every human's files). It is one match with no catch-all arm, so a new route fails to compile there until someone decides its class. (A new kind inside an existing route's payload, such as a new script, takes that route's class.)

app/RouteCost.roc, lines 17-89, trimmed

## it compiles. `zig build cost-check` (host/cost_check.zig) measures each
## probe of app/route_cost_probes.txt at 10 and 300 humans and holds it to
## its class, and `RouteCostSpec` holds each probe's route to the class its
## line names.
...
RouteCost :: [].{

	## How a route's file calls grow with the chat's humans: its cost class.
	Growth : [Constant, PerReaderPlaces, PerHuman]

	## The class of the route `choice`.
	growth_of : Route.Choice -> RouteCost.Growth
	growth_of = |choice|
		match choice {
			Open(ResumeOrBrowse) => Constant
			Open(ServeScript(_)) => Constant
			Open(ServeFavicon) => Constant
			Open(ServeAlertIcon) => Constant
			Open(ShowLogin) => Constant
			Open(SignIn) => Constant
			Open(SignOut) => Constant
			Open(StartGitHubSignIn) => Constant
			Open(FinishGitHubSignIn) => PerHuman
			...
			Open(RedeemDeviceCode) => PerHuman
			Open(ReturnToLogin) => Constant
			SignedInOnly(StartGitHubLink) => Constant
			SignedInOnly(ShowBrowse) => PerReaderPlaces
			SignedInOnly(ShowRecent) => PerReaderPlaces
			...
			SignedInOnly(ShowInvites) => PerHuman
			SignedInOnly(InviteHuman) => PerHuman
			SignedInOnly(InviteHumanAgain(_)) => PerHuman
			...
			SignedInOnly(SignOutOtherDevices) => Constant
			NotFound => Constant
			MethodNotAllowed(_) => Constant
		}

A declaration alone is a claim, so a probe measures it. zig build cost-check runs the real server on chats of 10 and 300 humans and counts each probe's reads, listings, writes and folder watches. A Constant probe must cost the same at both sizes, and any other must cost more at 300. So a route declared Constant that grows, or declared growing that doesn't, fails; the measure can't tell PerReaderPlaces from PerHuman. It counts file calls, not time, so a busy machine can't make it flaky.

app/route_cost_probes.txt, lines 10-31, trimmed

Constant anyone GET /favicon.ico
...
Constant anyone POST /login name=Tam&password=wrong
...
PerReaderPlaces human GET /chat
...

...

The gate runs the cost check last and holds the probes out of class at zero. The fixes that brought the routes into their classes came first: a plain read (a GET with no Authorization header) is admitted from its origin alone, and the server keeps the directory in memory, reading it again whenever its folders change. While the directory is unchanged, the favicon makes no file reads.

What it doesn't do: a route no probe reaches is declared, not measured. The counts are for a warm server with a quiet directory: the request after any change in the directory's folders reads the directory again, and a human's request that brings them online lists every other human's conversation with them, whatever its route. And a class bounds how calls grow with the number of humans, not with what one request names, such as a long transcript.

The lesson

The types answered "who acts?" They didn't ask "whose credential?", "what else must happen?" or "what does a request cost?" Each idiom adds one question:

  • Whose credential? A writer takes a proof, not an id. AccountProof and HumanClaim.Unclaimed are opaque, and only their own modules make them, so a call with a bare id doesn't compile. The credential check makes sure every other path to a credential names its proof.
  • What else must happen? Where the rule is "after this, that", and the type system can't force it, a check over Roc's parse tree holds it, at zero, in the gate.
  • What does a request cost? A match with no catch-all makes every route declare its class, and a measurement holds the probed routes to it.

In each case the rule has one home: one function ends streams, one type names their holders, one writer sets a password, each check's table judges every write, and one match names every route's cost.
