Roc on Shale

The programs listed here are written in Roc and run on Shale, a runtime for programs that work with files, folders and other programs. Each is a check or a report we run on our own code, and each has a page of its own that shows it in full.

What Roc brings

Roc is a fast, friendly, functional language.

  • Fast. Roc compiles to machine code.
  • Checked. The type checker infers every type, so a program needs few annotations and still has every call checked before it runs.
  • Pure by default. A function that reads a file is marked by its name and its type. Everything else is plain computation that a test can call directly.
  • Tested in place. Tests are expects, written beside the code they test.

Effects come from a platform

Every Roc application runs on a platform, which supplies its effects: reading files, reaching the network and the rest. A program has only the effects its platform offers. basic-cli, Roc's standard platform for command-line programs, offers a wide set: files and folders, the network, environment variables, the clock and more. The platform these examples use offers a narrower set, adds a few things of its own, and has Shale's runtime as its host, so each effect is a call into Shale, held to the limits Shale sets for the run. Everything else is plain Roc.

What it offers

  • Files: read and write a file, ask whether one exists, list, make and remove a folder, glob and grep.
  • Programs: run one, with a timeout, keeping the head, the tail or the whole of its output.
  • The rest: print, stop with a message, and read the script's arguments.

What it adds

  • Roc's parse tree. roc_tree! hands a program Roc's own parse of a file, so a check reads Roc code as Roc reads it.
  • Regular expressions, supplied by the host.
  • Shale's limits on every effect: budgets for a run's steps, reads and output; reads only beneath the run's root and its named mounts; a program run only when Shale's rules allow it; and a timeout on each one.

Beyond this platform

basic-cli also offers the network, environment variables, standard input and the clock. The programs here need only what's listed above. The platform's README explains how it works.

The examples

The examples are in sections. The first holds programs that find flaws in Roc code, and some that fix them too: Roc reading Roc, most of them through Roc's own parser. After it come programs that read Shale itself, then reports on Roc projects, then smaller programs over Zig. The shared packages the examples import are listed at the end, and each is shown once, on a page of its own.

Shale's own language

Shale is also a scripting language of its own, and each example began as a Shale script. Each example's page shows its Roc program, then the Shale script it was ported from, with both files colored by roc-syntax-color. Each port was checked against its original's output. The links at the top and end of each example's page go to the one before or after it, and back to its place here.

How the runtime is built

Shale's runtime is written in C, in its repository's c/ folder, and needs only Linux on x86-64, GCC and TCC.

  • One translation unit. c/shale.c takes in the whole runtime, so GCC sees every function at once and the release build is a single gcc -O2.
  • Two compilers. TCC compiles the whole program in a fraction of GCC's time, for the edit loop. GCC builds every binary we ship, with no LLVM involved.
  • Two tiers of checks. The fast tier runs every C test in seconds, on each edit. The full tier adds the release build, every test under ASan and UBSan, a -Werror build at -O2, and the cookbook's own tests, including the goldens behind the examples below. It runs on GitHub, before every merge. Each test was also proven once, by a planted fault, to be able to fail.
  • The builds are Shale scripts. A new machine builds its first shale by hand with TCC and GCC, and from then on Shale builds itself.

The Roc platform's host is that same C, with a small driver added. It's compiled once with gcc -O2 into an object and cached. Each Roc script is built by the pinned Roc compiler into an archive and linked with that object, and the program is cached by a hash of every file it's built from. The Roc runs on a stack of its own, takes its memory from an arena held to the run's budget, and has a CPU budget for its own computation.
